# 0006. Reports and CSV export: rationale

Build spec: [`index.md`](index.md).

## Context

This is feature 6 of `scope.md` and step 9 of the MVP demo flow (export a report as CSV). It stands on spec 0002 (sessions, `requireStaff`, the permission map with `reports.view` already granted to admin and coordinator and denied to supervisor), spec 0003 (volunteer totals computed from finalized attendance, never stored), spec 0004 (activities, assignments, the status rule that closed and cancelled are final), and spec 0005 (attendance, finalization: a finalized activity is always `closed`, so it can never be cancelled afterwards, and `attendanceFinalizedAt` marks the moment its numbers became official).

BAMX reports volunteer hours to donors and to its own leadership, usually by month or by year. The numbers must be the official ones: an activity whose attendance is still being taken would make a report change between two reads, and a report that disagrees with the volunteer detail screen would make staff distrust both. The data is small (hundreds to low thousands of volunteers, tens of activities a month), so the cost of aggregating at read time is not a concern; correctness and consistency are.

The export is the one place personal data deliberately leaves the system. Security is graded (the Cybersecurity course): exports must be limited to allowed roles on the server, recorded in the insert only `audit_log` (`AGENTS.md` lists every CSV export as an audited action), protected against CSV formula injection (a cell starting with `=`, `+`, `-`, or `@` runs as a formula when opened in Excel), and should carry as little personal data as the job needs. A stolen session that quietly downloads everything is the abuse case to slow down.

Constraints: Android phones in the field; dates shown in `es-MX`, timezone `America/Mexico_City`, stored as UTC; the CSV will mostly be opened in Excel on a Spanish Windows machine; Expo SDK 57 with no file or sharing module installed yet.

## Options considered

### Option 1: Aggregate in the app from existing endpoints

The app loads activity details and volunteer details it already has endpoints for and sums the numbers on the phone; the CSV is built on the phone too.

**Pros**:
- No new server code for the on screen numbers.

**Cons**:
- Downloads every record to the phone to show three totals; slow on field connections.
- The CSV would be built on the client, which `AGENTS.md` forbids (exports are generated by the API), and the server could not audit or rate limit an export it never sees.
- Supervisors can already read activities and volunteers, so a client built report would bypass the `reports.view` rule.

### Option 2: Server aggregation at read time, one query function per report shared by JSON and CSV (recommended)

New `server/src/reports.ts` with one function per report (`summary`, `volunteerHours`, `activityAttendance`) that runs a MongoDB aggregation over `activities` → `assignments` → `attendance` for the range. The JSON route pages the result; the CSV route takes all rows from the same function, formats them, audits, and sends. Nothing is stored.

**Pros**:
- One source for each number, so the screen and the file can never disagree.
- Matches spec 0003's rule that totals are computed, never stored, so reports and the volunteer detail agree.
- Role check, audit, rate limit, and injection guard all sit on the server where they can't be skipped.

**Cons**:
- Each request aggregates from scratch; fine at BAMX's size, would need rethinking at hundreds of thousands of records.
- "All active volunteers, zeros too" means merging the aggregation with the volunteer list in memory before paging, which costs one read of every candidate volunteer's name per request.

### Option 3: Stored monthly rollups

A rollup collection updated whenever attendance is finalized or corrected, holding hours per volunteer per month.

**Pros**:
- Reports read a few small documents.

**Cons**:
- A stored derived value that every finalize and admin correction must keep in step; one missed path and reports drift from the volunteer detail.
- Ranges are by day, not month, so rollups would not answer custom ranges anyway.
- Solves a performance problem nobody has measured.

## Rationale

The forces that decide this are consistency and the security grade, not speed. Spec 0003 already settled that hour totals are computed from finalized attendance and never stored; a report that summed differently, or a rollup that lagged behind an admin correction, would make the Reportes tab and the volunteer detail disagree, and staff would trust neither. Option 2 is the only one where the screen, the CSV, and the volunteer detail all follow the same rule.

`AGENTS.md` requires exports to be generated by the API, audited, limited by role, and guarded against formula injection. Option 1 cannot meet that at all, because the server never sees the export. Option 3 meets it but adds a stored derived value that every attendance write path (record, mark all, finalize, admin correction) would have to update in the same transaction, for a performance gain BAMX's data size doesn't need.

The data minimization choice (names and numbers only) and the per staff rate limit both answer the same threat: a session token that leaks. A leaked token can still read reports, but each file it pulls carries no contact data, is limited in number, and leaves a row in an insert only log naming the account.

### Update 2026-10-13: a "Descargar" button

After the first build, the engineer asked for a real download, not only the share sheet (Android's sheet often has no "save to phone" target). Options weighed:

- **Pick a folder each time (chosen).** `Directory.pickDirectoryAsync` from `expo-file-system`, already installed. No storage permission, the app only gets access to the one folder staff choose, and the file goes exactly where they decide. Cost: Android 11+ refuses the Download folder itself in this picker, so staff save into a folder inside it.
- **Always save to Descargas.** One tap, but on Android 10+ that only works through MediaStore, which `expo-file-system` doesn't expose, so it needs another native module, and the file lands in shared storage without the person choosing where.
- **Share only, relabel the button.** No new behavior, but staff still can't simply keep the file on the phone.

The folder is picked before the CSV is requested so a cancelled pick never reaches the server: no export in the audit log for a file nobody received.
